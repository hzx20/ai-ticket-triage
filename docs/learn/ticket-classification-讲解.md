# AI 工单分类链路讲解

## 这次解决了什么问题

最初仅把分类任务放进进程内线程池：提交后进程退出，任务可能丢失；模型运行期间工单被修改，旧结果也可能覆盖新内容。缓存计算标记过期后，旧线程还可能删除其他线程的标记。

现在创建工单时，把需要自动分类的任务写入 MySQL；调度器定期扫描并认领任务。设计目标是故障后可重试、旧结果不能覆盖新版本。它属于**至少一次尝试**：进程中断、租约超时或缓存等待超时都可能导致模型重复调用，并不保证恰好一次或绝不重复计费。

## 代码怎么实现

1. **事务与持久任务**：`TicketServiceImpl.create` 在同一数据库事务中创建工单和待处理任务。事务回滚时两者一起回滚。任务写入成功后，扫描器读取已提交的任务；线程池满时不删除任务，等待后续扫描。人工指定的有效分类直接保存，不创建自动分类任务。
2. **租约和结果提交**：`TicketClassifyJobRunner` 在工作线程认领任务，使用任务 ID、租户 ID、状态及到期时间做原子更新，生成随机 token 和 120 秒租约。模型调用在事务外执行；最终在一个短事务中通过 `SELECT ... FOR UPDATE` 检查 token、状态和租约，再写回工单并更新任务状态。旧 token 或过期租约不能通过这道检查。失败按退避间隔重试，达到 10 次转为 `FAILED`；最终一次执行时进程退出也会在租约到期后转失败。
3. **版本与人工修改**：工单 `revision` 从 0 开始。人工修改携带读取时的版本，SQL 以工单 ID、租户和版本为条件，成功后版本加一；条件不匹配就提示刷新。分类结果也按快照版本条件更新并加一。因此内容从 A 改为 B 再改回 A，旧任务的版本仍不匹配，不依赖数据库字符串排序规则判断是否变化。
4. **缓存**：缓存 key 包含租户 ID 和工单内容摘要。持有唯一随机标记的计算者通过 Redis Lua 原子比较并写入或释放；规则兜底结果不缓存。抢不到标记的请求短轮询，等不到就自行调用模型，因此缓存是优化，不是严格的并发去重保证。Redis 不可用时仍可直接分类。
5. **租户与访问边界**：调度器跨租户扫描只读取任务 ID 和租户 ID，执行前检查租户并恢复该任务的租户上下文；任务操作显式限制租户。**同一租户内的工单按当前项目权限配置共享**，不要把行级租户隔离描述成“同租户每个人只能看自己的工单”。

## 为什么这样设计

- 仅用 `afterCommit` 或内存队列，能避开部分事务可见性问题，却无法在提交后、入队前或进程退出后恢复任务；数据库持久任务保留了待处理记录。
- 单靠检查内容是否相等无法识别 A→B→A，也会受到数据库排序规则影响；数字版本能让每次成功修改都留下变化。它依赖所有相关写路径遵守同一版本约定。
- 仅检查租约是否过期不够：旧工作线程可能在另一个线程重新认领后继续运行。随机 token 加原子条件更新，在最终写回事务前限制有效持有者；这仍不能撤销旧线程已经发出的外部模型请求。
- 缓存标记若直接 `DEL`，旧持有者可能删除新标记；Lua 把“比较所有权”和“更新或删除”放在 Redis 一次原子操作中。即便如此，短轮询结束后仍可能并发调用模型。

## 涉及的概念和验证边界

**事务**保证同一事务里的数据库更改一起提交或回滚，不覆盖事务外的模型调用。**租约**给处理者一段有效期；**fencing** 在写结果前检查当前持有者，拒绝失效处理者的写入。**乐观并发控制**用读取到的版本作为更新条件；受影响行数为 0 表示快照已过期或记录不可见。

本地隔离 MySQL/Redis 的目标集成测试曾执行 17 项且无跳过：覆盖 Redis 所有权、MySQL 任务并发认领、过期 token、事务回滚、租户过滤、历史回填和版本 ABA。MySQL 任务测试只替换随机表名执行仓库 SQL，不能单凭它证明完整应用启动、线上负载表现或跨进程故障全部通过。完整门禁与端到端结果以最终测试报告为准。

## 三个面试自测问题

1. 如果工单事务提交后服务立即重启，任务如何找到？如果模型已经调用但结果尚未提交，为什么可能再次计费？
2. 两个工作线程先后认领同一任务，旧线程在租约过期后返回结果；token、行锁和 `revision` 各防止什么？它们分别不能解决什么？
3. 同一租户内两名用户提交相同内容时缓存如何工作？抢不到标记后为什么仍可能调用模型，同租户共享和跨租户隔离分别意味着什么？
